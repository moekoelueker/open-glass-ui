# Accessibility

OpenGlass UI targets WCAG 2.2 AA and treats accessibility adaptation as part of
the material contract. This target is not a certification: consumers must test
their content, colors, composition, and application behavior.

## Core contract

1. Semantics, text, focus, and interaction remain native DOM.
2. Refraction, transparency, color, or motion is never the only state signal.
3. Unsupported effects retain an intentional readable CSS or opaque material.
4. Reduced motion, reduced transparency, and forced colors are designed states.
5. Actual foreground/background pairs are tested, including hostile media.

The forty recipes use native buttons, inputs, fieldsets, labels, navigation,
progress elements, and ARIA relationships. WebGL canvases are decorative by
default; interactive content must remain in the DOM.

## Consumer responsibilities

- Give every control a visible label or an accessible name.
- Pass `aria-label` to every `IconButton`; do not rely on the icon glyph.
- Preserve labels, descriptions, errors, roles, and `aria-*` state generated by
  recipes.
- Use text, icons, or explicit state attributes in addition to material/color.
- Keep normal text at least 4.5:1, large text at least 3:1, and essential
  boundaries/state indicators at least 3:1.
- Verify focus indicators over the real background.
- Keep targets large enough for touch and allow browser zoom/reflow.
- Announce asynchronous application outcomes when the recipe alone cannot know
  them.

```tsx
import { IconButton, Switch, TextField } from "open-glass-ui";

export function AccessibleControls() {
  return (
    <>
      <IconButton aria-label="Close settings">
        <span aria-hidden="true">×</span>
      </IconButton>
      <Switch
        label="Share activity"
        description="Allow teammates to see when this file was opened."
      />
      <TextField
        label="Workspace name"
        error="Use at least three characters."
        aria-required="true"
      />
    </>
  );
}
```

## Keyboard behavior

Native controls retain their platform keyboard behavior. Composite recipes add
the expected patterns:

- `Tabs`: Arrow Left/Right, Home, End, roving tab stop.
- `Menu`: Arrow Up/Down, Home, End, typeahead, Escape, Tab dismissal, focus
  restoration.
- `Popover`: Escape and outside-pointer dismissal with focus restoration.
- `Dialog` and `Drawer`: initial focus, Tab containment, Escape, inert
  background, scroll lock, and trigger-focus restoration.
- `Accordion`: buttons expose `aria-expanded` and panel relationships.

Do not put interactive descendants inside another button, link, or native
control. Test the complete workflow using only a keyboard.

## Adaptive rendering

`GlassProvider` reads system preferences after hydration:

```tsx
<GlassProvider renderer="auto" quality="auto" motion="system">
  <GlassThemeProvider appearance="system">{children}</GlassThemeProvider>
</GlassProvider>
```

- `prefers-reduced-motion: reduce` turns provider-driven pointer motion off and
  recipe CSS removes or slows nonessential animation.
- `prefers-reduced-transparency: reduce`, where supported, chooses opaque
  material tokens and blocks enhanced renderers.
- `forced-colors: active` chooses system colors, removes optical effects, and
  preserves visible boundaries and selected states.
- Unsupported SVG/WebGL capability falls back to CSS without removing content.

Reduced-transparency detection is not uniformly implemented. Applications with
stricter requirements should also provide an explicit “reduce transparency”
setting or opaque application theme and test it independently.

## Theme and contrast

Neutral high-contrast light and dark themes are the defaults.
`createGlassTheme()` derives a readable accent foreground, but translucent
surfaces change with their backdrop. Measure contrast on representative
photographic, noisy, light, dark, and high-chroma sources—not only on a flat
design canvas.

Prefer `regular` or `frosted` for overlays and text-heavy transient surfaces.
Use `clear` only where the source remains controlled and legibility is proven.
Never place long-form content behind continuous refraction.

## Test before release

Automated checks are a floor. For each public component and supported browser,
review:

- accessible name, role, value, state, and relationships;
- Tab order, arrow-key behavior, Escape, focus visibility, and restoration;
- 200%, 300%, and 400% zoom/reflow;
- reduced motion, reduced transparency, and forced colors;
- light/dark themes and difficult backgrounds;
- disabled, invalid, selected, open, loading, and error states;
- touch target size and mobile orientation;
- VoiceOver on macOS/iOS and NVDA on Windows; and
- DOM order and announcements with the WebGL/SVG effect unavailable.

The current research build has automated axe, keyboard, focus, fallback, and
three-browser evidence. Physical-device screen-reader and high-zoom review
remain release gates; do not present the project as accessibility-certified.
